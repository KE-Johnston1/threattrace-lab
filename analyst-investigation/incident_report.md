# Incident Report: TT-SSH-001

## Suspected SSH Brute-Force / Account Compromise

**Severity:** HIGH  
**Detection Rule:** `SSH-BRUTE-001`  
**Status:** Investigation required  
**Environment:** Synthetic / controlled lab

---

## 1. Executive Summary

ThreatTrace generated a synthetic SSH authentication scenario in which a single source repeatedly attempted to authenticate to an SSH service. The activity included multiple failed authentication attempts against the `admin` account followed by a successful `admin` authentication from the same source.

The pattern triggered the `SSH-BRUTE-001` detection rule and was assessed as **HIGH severity** because the successful authentication creates the possibility of account compromise.

No real systems or external services were targeted. All activity is synthetic telemetry generated for defensive security analysis.

## 6. Analyst Assessment

**Initial assessment:** Suspicious authentication activity with potential account compromise.

The evidence is sufficient to escalate the alert for investigation because:

1. The activity originates from a single source.
2. Multiple authentication failures occur within a short period.
3. The `admin` account is repeatedly targeted.
4. Authentication subsequently succeeds from the same source.

The lab does not provide evidence of actual post-authentication compromise. Therefore, the analyst should **not** claim that compromise occurred without additional telemetry.

---

## 7. Recommended Response

### Immediate containment

- Validate whether the successful `admin` authentication was authorised.
- Investigate the source system associated with `10.10.10.50`.
- Review the successful SSH session and any activity immediately following authentication.
- Search other available telemetry for the source IP and account.

### If compromise is confirmed

- Disable or protect the affected account according to organisational procedure.
- Rotate credentials and review authentication controls.
- Block or restrict the malicious source where appropriate.
- Review affected systems for persistence or further unauthorised activity.

### Preventive controls

- Enforce strong authentication controls.
- Use MFA where supported.
- Apply SSH access restrictions and rate limiting.
- Monitor authentication failures and successful logins together rather than independently.
- Maintain centralised security logging.

---

## 8. Lessons Learned

This scenario demonstrates why a SOC should correlate events rather than treat individual failed logins as isolated incidents.

A sequence of authentication failures followed by a successful login provides stronger evidence and a more actionable detection than a simple count of failed attempts.
